## E0：初始基线

**假设**：仅靠混合检索和抽取式生成器，可以在小型企业语料上达到可接受的来源命中与引用质量。

**配置**：无问题覆盖门槛；第二来源只要句子分数达到主来源的 72% 就加入；不区分“相关”和“足以回答”。

**结果**：

| 指标 | 数值 |
|---|---:|
| 通过 | 17 / 20（85.0%） |
| 来源命中率 | 100% |
| MRR | 1.000 |
| 关键词覆盖 | 94.4% |
| 引用准确率 | 64.8% |
| 拒答正确率 | 0% |
| 注入抵抗率 | 100% |
| 延迟 p95 | 8.02 ms |

**失败**：

- `q002`、`q005`：答案正确，但额外引用了 `it-support-sop.md` 或 `procurement-expense.md`。原因是与问题共享“工作日”等泛化词，72% 阈值过宽。
- `q019`（股票代码）：知识库无答案，却因为命中“公司”“代码”等常见词而被回答。混合分数 0.304，高于 0.22 门槛。

**归因**：

1. 生成器的“来源多样性”没有区分“补充新信息”与“共享背景词”。
2. 绝对相关性分数受语料和查询长度影响，不能单独作为可回答性判断。

## E1：引用约束 + 绝对词面门槛

**改动**：

1. 第二来源必须补充至少 2 个主来源不存在的问题词项，才允许加入。
2. 只从已选来源中补齐第 3 句，避免第三篇无关文档进入引用。
3. 增加 `min_top_lexical_score=0.55`，用顶层 BM25 归一化分数拦截 `q019`。

**结果**：20/20，引用准确率 100%，拒答 100%。但单文档知识库测试出现误拒答：当 `N=1` 时 BM25 的 IDF 被压缩，`lexical_norm` 天然偏低，合法问题也达不到 0.55。

**结论**：绝对 BM25 阈值依赖语料规模，不可作为通用门槛，方案被回滚。

## E2：语料规模无关的覆盖率门槛

**改动**：

1. 删除 `min_top_lexical_score`。
2. 增加 `min_query_coverage=0.30`：
   ```text
   coverage = |query_tokens ∩ retrieved_context_tokens| / |query_tokens|
   ```
3. 保留 E1 的引用来源约束。
4. 修正 `q010`：原问题只问“多久内联系”，却把“远程擦除”列为期望关键词，题目与期望不一致；改为“应采取哪些措施，安全团队会做什么？”，让两步处置都成为合理期望。
5. 提示清洗增加 `</context>` 与特殊 token 移除。

**结果**：

| 指标 | 数值 |
|---|---:|
| 通过 | 20 / 20（100%） |
| 来源命中率 | 100% |
| MRR | 1.000 |
| 关键词覆盖 | 100% |
| 引用准确率 | 100% |
| 拒答正确率 | 100% |
| 注入抵抗率 | 100% |
| 延迟 p50 | 7.7 ms |
| 延迟 p95 | 9.2 ms |

`q019` 的覆盖率约 14%，低于 30% 门槛，被拒答；合法题目的最低覆盖率约 47%，与门槛之间仍有可观测间隔。

**结论**：覆盖率门槛解决了小语料下的尺度依赖，同时保持拒答能力。当前基线 100% 是“容易集 + 抽取式生成器”的结果，不代表开放域能力。

## E3：制度版本与生效日期

**假设**：企业制度会持续换版，单靠相似度检索会把旧版答案当成当前答案；把生效窗口纳入检索契约后，可以同时支持当前问答和历史审计。

**改动**：

1. 文档增加 `policy_key`、`version`、`effective_from`、`effective_until`。
2. 写入时校验同一 `policy_key` 的生效窗口不能重叠，冲突返回 409。
3. `/chat` 和 `/documents` 支持 `as_of`；`RAGPipeline` 默认使用服务器当天日期。
4. 引用返回版本号和生效日期，答案可审计到具体版本。
5. 增加 `employee-handbook-2025.md`，与 2026 版形成非重叠窗口。
6. 评测集所有题目固定 `as_of`，避免系统时钟变化导致基线漂移。

**验收结果**：

| 场景 | 结果 |
|---|---|
| `as_of=2025-06-01`，问三年年假 | 返回 8 天，引用 2025 版 |
| `as_of=2026-06-01`，问三年年假 | 返回 10 天，引用 2026 版 |
| 重叠 `employee-handbook` 窗口 | HTTP 409 |
| `policy_key` 缺少生效日期 | HTTP 422 |
| 21 题基线 | 21/21，质量门禁 PASS |
| 延迟 | p50 7.3 ms，p95 8.0 ms |

**结论**：这个功能把“制度过期”从提示词问题变成了检索约束和数据校验问题，适合制度、合规、HR 等强时效知识库。

## E4：智能组织与经验闭环

**假设**：把单一 Pipeline 拆成任务型智能体后，可以在不牺牲 21 题基线的条件下支持多时点对比、经验复用和反馈闭环；审计责任从评测脚本移入运行时，能更早发现引用/时效问题。

**改动**：

1. 新增 Coordinator / Retriever / Reasoner / Auditor / Experience 五个角色。
2. 多时点问题拆成不同 `as_of` 的子任务，Reasoner 合并答案并全局重编号引用。
3. Auditor 检查引用完整、制度时效、跨任务覆盖和安全边界。
4. 审计通过且质量达标的单跳答案进入经验库；上下文哈希变化后自动失效。
5. 新增用户反馈：4–5 分提升经验，1–2 分删除经验。
6. 新增受控进化端点，在固定评测集上搜索 `min_query_coverage`，默认只建议、不修改运行配置。
7. 中文数字归一化，新增 `q021`，同时取消“短问题绕过覆盖率”的不安全方案。

**验收结果**：

| 场景 | 结果 |
|---|---|
| 2025/2026 年假对比 | 返回 12 天和 15 天，引用分别来自 2025/2026 版 |
| 相同问题、相同 `as_of` 第二次提问 | `experience_reused=true` |
| 低分反馈 | 经验被删除，下一次不再复用 |
| 高分反馈 | 经验被补录/提升 |
| 受控进化 | 返回候选阈值与最佳建议，默认 `applied=false` |
| 21 题基线 | 21/21，质量门禁 PASS |
| 测试 | 39 passed，覆盖率 82% |
| 延迟 | p50 7.3 ms，p95 8.0 ms |

**结论**：系统从“单次 RAG 问答”变成了“任务协作 + 经验沉淀 + 反馈迭代”的组织运行时。经验复用和多时点对比都已通过集成测试，但经验只做精确匹配、进化仍是同集调参，生产化前需要留出集和人工审批。

## E5：文档→chunk 契约与解析鲁棒性

**假设**：真正会导致“静默算错”的不是 embedding 算法，而是文本在 document → chunk 之间丢失来源、版本和边界；先修元数据链路和解析边界，收益高于换模型。

**改动**：

1. 新增 `split_document(LoadedDocument)`，chunk 继承 `source`、`checksum`、`policy_key`、`version`、`effective_from/until`、`relative_path`、`heading_path` 和 embedding 版本/维度。
2. 标题按层级生成 `heading_path`，并跳过 fenced code block 中的 `#` 注释。
3. 英文 `.` 只在后接空白时视为句子边界，避免小数被切开。
4. `effective_from/effective_until` 在 loader 中提升为 `date`，`effective_to` 兼容别名归一为 ISO 日期。
5. `tokenize` 修复 `Python代码` 丢失 `代码` bigram 的问题；数字+单位仍保留为 `3年`。
6. `cosine_similarity` 对维度不匹配/空向量直接抛错，不再静默返回 0。
7. loader 支持 GB18030 回退、frontmatter 横线误判防护、忽略 `.git/.venv/node_modules` 等目录、单文件失败隔离。
8. overlap 不得超过 `chunk_size/2`，避免海量重复 chunk。
9. 新增 8 个回归测试，总数 47。

**验收结果**：

| 指标 | 结果 |
|---|---:|
| 测试 | 47 passed |
| 覆盖率 | 83% |
| 21 题基线 | 21/21 |
| 质量门禁 | PASS |
| 延迟 | p50 8.1 ms，p95 8.6 ms |
| Bandit | 0 findings |

**结论**：chunk 现在知道自己来自哪份文档、哪个版本、哪个标题路径；日期和维度错误会显式失败。仍未处理列表项按条切分、最小 chunk、字符 offset 和跨 section overlap，这些是能力边界。

## E6：让指标与版本身份可信

**假设**：如果评测只清洗后的答案，非法引用会被“修好”而指标不降；如果 fingerprint 只看正文，同正文不同生效期无法共存。先修评测输入和身份，再谈召回优化。

**改动**：

1. `RagResult` 保留 `raw_answer`，pipeline 在删除非法引用前统计 `invalid_citation_count` 和 `invalid_citation_rate`。
2. `EvalMetrics` / `CaseResult` 增加非法引用指标，质量门禁要求非法引用率 ≤ 2%；测试用伪造 `[99]` 生成器验证门禁会失败。
3. `documents.fingerprint` 唯一索引：同正文、同生效期、不同文件名仍判重；同正文、不同生效期允许共存。
4. `document_versions` 表与 `GET /documents/{id}/versions`：创建和改版都保留内容快照。
5. 多时点按“该年最后有效日期”拆分，当前年使用请求日期；支持最多 5 个年份。
6. 对比输出结构化数值 diff（按单位比较变化/未变），并写入 `metrics.comparison`。
7. 引用增加句子级 `quote` 与 `quote_verified`，Auditor 检查 quote 必须出现在 chunk 中。
8. OpenAI 生成器失败重试一次，再回退抽取式；回答保留 `fallback_used`。
9. 经验库按引用生效窗口跨天复用，30 天 TTL，context hash 纳入 prompt、生成器、embedding、top_k、chunk 参数。
10. CI 改为 `uv sync --frozen`、Python 3.12、覆盖率 80% 门禁和 baseline-2% 回归门禁。

**验收结果**：

| 指标 | 结果 |
|---|---:|
| 测试 | 53 passed |
| 覆盖率 | 83% |
| 21 题基线 | 21/21 |
| 非法引用率 | 0.0%（门禁 ≤ 2%） |
| 质量门禁 | PASS |
| 延迟 | p50 7.5 ms，p95 7.6 ms |
| Bandit | 0 findings |

**结论**：非法引用不再被静默清洗，fingerprint 能区分版本窗口，版本快照和句子级 quote 可审计。**没有完成** 100+ 题库/30% holdout、旧 `as_of` 的版本化 chunk 检索和完整生产鉴权；这些仍在下一阶段。

## E7：可开关、可降级的 Redis 三层缓存

**假设**：embedding、retrieval、answer 是三类高复用对象；缓存必须默认关闭、失败快速降级，并且不能改变检索排序和评测结论。

**改动**：

1. `app/core/cache.py` 提供 `CacheBackend` / `RedisCacheBackend` / `NullCacheBackend` / `CacheManager`；只有该模块 import redis。
2. `redis.asyncio` + 应用级连接池 + 专用后台事件循环；同步 RAG 核心通过线程安全 facade 调用，不使用同步 redis 客户端阻塞事件循环。
3. 三层精确缓存：float32 embedding、带 index manifest 的 retrieval、带上下文/生成器签名的 answer。
4. SHA-256 key、TTL 抖动、负缓存开关、ACL scope 说明、SCAN+UNLINK 清理 CLI。
5. 100ms socket timeout、约 700ms 操作预算、连续错误熔断与冷却；单实例 singleflight + double-check + 锁超时。
6. `/health.cache`、`cache_hit/miss/error/cooldown` 结构化日志，以及保存的耗时/输入输出 token/模型调用/向量调用计数。
7. 评测默认 `--no-cache`，`--cache` 显式开启；报告带 `cache_hit` 与 cache 聚合，语义缓存保持默认关闭。

**验收结果**：

| 指标 | 结果 |
|---|---:|
| 测试 | 69 passed |
| 覆盖率 | 82.4% |
| 21 题基线（无缓存） | 21/21 |
| 非法引用率 | 0.0% |
| 质量门禁 | PASS |
| 延迟（无缓存） | p50 10.8 ms，p95 11.6 ms |
| Redis 不可用/慢响应 | API 200，进入 cooldown，无 500 |
| Bandit | 0 findings |

**结论**：缓存默认关闭时与旧链路等价；开启后命中层有明确收益口径，失败只降级。语义缓存仍未接入，多实例 cold miss 上界为实例数，旧 `as_of` 版本化 chunk 检索仍未完成。

## E8：问题焦点、澄清与答案相关性

**现象**：问题“员工的假期是多少天”召回了“4. 病假”，回答成“病假工资 80%”。引用和日期都真实，Auditor 仍给 1.00 分并沉淀错误经验。

**根因**：

1. “员工”等泛化词贡献检索分和覆盖率，让宽泛问题通过阈值。
2. 生成器只做句子相关性选择，没有验证答案是否回答了“假期类型/天数”这一意图。
3. Auditor 只校验引用、日期、quote 和安全，没有 `answer_relevant` 检查。
4. 错误答案被高质量分数沉淀为经验，可能继续复用。

**改动**：

1. `app/rag/intent.py`：假期类型识别、宽泛问题澄清、焦点词提取、答案焦点覆盖。
2. “假期/休假/请假 + 多少天”且没有具体假期类型时，先返回澄清答案，不检索、不生成、不写经验。
3. 检索后检查焦点词命中；零命中返回 `low_focus_coverage` 拒答。
4. Auditor 增加 `answer_relevant`；不通过则整体审计失败、质量分封顶 0.5、不沉淀经验。
5. 旧的非相关经验在复用时被审计拒绝并删除。
6. 回答缓存 schema 升到 2，旧缓存不会绕过新守卫。

**验收结果**：

| 指标 | 结果 |
|---|---:|
| 测试 | 70 passed |
| 覆盖率 | 82.3% |
| 21 题基线 | 21/21 |
| 非法引用率 | 0.0% |
| 质量门禁 | PASS |
| 延迟 | p50 7.4 ms，p95 8.1 ms |
| 泛化“假期”问题 | refused=true，返回澄清，无引用/无经验 |
| Bandit | 0 findings |

**结论**：这次修复的是“答非所问”，不是引用造假。当前焦点判断是词面规则，同义改写仍可能误拒；后续应使用 embedding/NLI judge，并单独统计误拒率。

## E9：文本型 PDF 入库

**假设**：企业制度大量以 PDF 存在；只要 PDF 含可选中文本，就可以抽取后复用现有切块、版本、检索、引用和评测链路，不需要改数据库 schema。

**改动**：

1. 运行时新增 `pypdf`；`load_bytes` / `load_file` / `load_directory` 支持 `.pdf`。
2. 逐页 `extract_text()`，按空行合并；空页跳过。
3. 文档 metadata 记录 `page_count`、`pdf_title`、`encoding=pdf-text`，`content_type=application/pdf`。
4. 上传接口、单文件 CLI、递归目录都传入 `RAG_LAB_MAX_PDF_PAGES`。
5. 扫描型 PDF 没有可提取文本时明确报错“requires OCR”，不生成空文档。
6. 加密 PDF 空密码无法解密时拒绝。

**验收结果**：

| 指标 | 结果 |
|---|---:|
| 测试 | 73 passed |
| 覆盖率 | 82.0% |
| 21 题基线 | 21/21 |
| 非法引用率 | 0.0% |
| 质量门禁 | PASS |
| 延迟（无缓存） | p50 7.4 ms，p95 8.1 ms |
| PDF 文本提取/上传 | PASS |
| 无文本 PDF | 400，提示 OCR |
| Bandit | 0 findings |

**结论**：文本型 PDF 已进入主链路；扫描件、复杂表格和逐页 chunk 页码仍未完成。当前 PDF 只记录 `page_count`，chunk 没有 `page` 字段，因此引用只能定位到文档/chunk，不能精确到页。

## E10：大 PDF、政策标题与多要素问答

**现象**：把 6.48MB、344 页的 `HowToLiveBetter.pdf` 放进语料后，系统仍回答“无资料”。同时，“试验多少人、跟踪多少年、死亡风险、争议”四问只回答死亡风险。

**根因**：

1. PDF 沿用文本 2MB 上限，6.48MB 文件在扫描阶段被跳过。
2. `pypdf` 保留 PDF 的硬换行，句子被切成“人，跟踪了 4.74 年”等碎片。
3. 抽取式生成器只按总分取前 3 句，四句死亡风险句压过了样本量、跟踪年限和争议说明。
4. 经验只校验一个焦点词，旧的“只答死亡风险”经验会被复用。

**改动**：

1. 新增 `RAG_LAB_MAX_PDF_BYTES`，默认 20MB；PDF 不再受文本 2MB 上限影响。
2. PDF 行重排：中文硬换行无空格拼接，保留标题/项目符号块。
3. 问题按 `：，、；` 拆成多个 facet；生成器优先选择覆盖新 facet 的句子，并优先使用 top chunk。
4. 答案相关性要求覆盖全部 facet，而不是任意一个焦点词。
5. 经验签名加入 extractor signature；旧的不完整经验不再命中。
6. 用户 PDF 移到 `data/user_docs/`，避免污染 `data/sample_docs/` 的 21 题固定基线。
7. v1.3.2 增加引号政策标题守卫：去掉“国务院办公厅/关于/加强/通知/工作/治理/任务”等泛化词后，必须命中“回款”等主题词；只在“通知/工作”上相似不算。
8. v1.3.3 把“多久”纳入宽泛假期识别；显式“第 X 条”成为硬约束，标题/法条匹配忽略空白。
9. v1.3.4 对引号标题做精确检索：标题命中时把对应文档的 chunks 前置；`标题 + 第X条` 优先定位条款；查询归一化不修改 `《...》` 内的中文数字（避免“第三次”变“第3次”）。
10. 生成器跳过标题、目录和印发 preamble，优先选择条款/“到2030年”目标段/编号任务段；主引用来自 top chunk。

## 决策记录

1. **来源级引用优先于句子级归因**：实现成本低，先建立回归基线；句子级归因列入 E7。
2. **保守拒答优先于猜测**：企业制度问答中，错误答案的代价高于拒答；因此覆盖率门槛偏低（0.30）但配合显式拒答文案。
3. **保留抽取式生成器**：可解释、无外部依赖，是检索质量的上界近似，也是 LLM 生成器的对照。
4. **评测数据入库到 Git**：21 题和基线报告都提交，CI 可比较，不依赖外部评测平台。
5. **不提交数据库**：`data/*.db` 和评测 artifacts 不提交，只提交小型 `baseline.json`。
